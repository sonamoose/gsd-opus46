# GSD-Opus46 모드 분기 개선

## What This Is

GSD-Opus46의 `/gsd:new-project` 커맨드를 개선하여, 기존 코드베이스가 있는 프로젝트(브라운필드)와 신규 프로젝트(그린필드)를 자동 감지하고 각각 최적화된 워크플로우로 분기하는 시스템. 기존 코드가 있으면 맥락 중심으로 분석 후 수정/개선 목적을 파악하고, 신규면 설계 중심으로 깊은 질문을 통해 꼼꼼하게 설계한다.

## Core Value

코드 존재 여부에 따라 자동으로 최적의 워크플로우를 제공하여, 기존 코드의 통찰력을 유지하면서 작업하거나 신규 프로젝트를 꼼꼼하게 설계할 수 있게 한다.

## Requirements

### Validated

- ✓ 신규 프로젝트 모드 — 설계 중심 질문→연구→요구사항→로드맵 파이프라인 (existing)
- ✓ 브라운필드 감지 — 코드 파일/패키지 매니저 존재 여부 확인 (existing)
- ✓ 코드베이스 매핑 — /gsd:map-codebase로 구조 분석 (existing)
- ✓ 커맨드 체계 — 30개 슬래시 커맨드, 11개 에이전트, 워크플로우 구조 (existing)
- ✓ 연구 에이전트 — 4개 병렬 researcher 스폰 (existing)

### Active

- [ ] 자동 모드 감지 — 코드 존재 여부로 신규/기존 모드 자동 판단
- [ ] 기존 코드베이스 4방면 자동 분석 — 구조/아키텍처, 기술 스택, 문제점/기술부채, 테스트 상태
- [ ] 분석 결과 요약 제시 — 사용자에게 코드베이스 현황을 명확하게 보여줌
- [ ] 수정/개선 목적 확인 — 분석 결과 기반으로 버그 수정 vs 기능 개선 선택
- [ ] 목적별 워크플로우 분기 — 수정 모드와 개선 모드 각각의 계획→실행 파이프라인
- [ ] 기존 코드 통찰력 유지 — 분석 결과가 이후 계획/실행 단계에서 참조됨

### Out of Scope

- 별도 커맨드 분리 — /gsd:new-project 하나에서 내부 분기로 처리
- 실시간 코드 모니터링 — 세션 중 코드 변경 자동 감지는 범위 밖
- 기존 에이전트 구조 변경 — 현재 에이전트 체계는 유지하고 새 에이전트/워크플로우만 추가

## Context

- GSD-Opus46은 Claude Code 위에서 동작하는 프로젝트 관리 프레임워크
- 현재 `/gsd:new-project`은 브라운필드 감지는 하지만 코드베이스 매핑 제안만 하고, 이후 흐름은 신규와 동일
- 기존 코드가 있는 경우 "무엇을 만들 것인가"보다 "무엇이 문제인가 / 무엇을 개선할 것인가"가 핵심 질문
- 커맨드(commands/) → 워크플로우(workflows/) → 에이전트(agents/) 3계층 아키텍처
- `.planning/` 디렉토리에 모든 프로젝트 상태가 저장됨

## Constraints

- **아키텍처**: commands → workflows → agents 3계층 구조를 따라야 함
- **진입점**: /gsd:new-project 하나의 커맨드에서 분기 — 별도 커맨드 추가 안 함
- **호환성**: 기존 신규 프로젝트 모드의 동작을 깨뜨리지 않아야 함
- **출력 형식**: GSD UI 브랜드 패턴(배너, 체크포인트, 상태 심볼) 준수

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| /gsd:new-project 내부 분기 | 사용자가 모드를 선택할 필요 없이 자동 감지로 최적 흐름 제공 | — Pending |
| 코드 존재 여부로 자동 감지 | 가장 직관적이고 정확한 판단 기준 | — Pending |
| 4방면 자동 분석 (구조, 스택, 문제점, 테스트) | 코드베이스의 전체 맥락을 빠짐없이 파악 | — Pending |
| 분석 후 수정/개선 선택 | 사용자 목적에 따라 이후 워크플로우가 달라져야 함 | — Pending |
