  <action>
Create `get-shit-done/templates/brownfield-summary.md` following the exact structure of existing codebase templates (e.g., `architecture.md`). The template defines the output format for `.planning/brownfield-analysis.md`.

**Template structure (follow existing pattern):**

1. **Top-level purpose statement** — explain that this template guides synthesis of 7 codebase documents into a single user-facing summary.

2. **`## File Template`** section — the markdown structure the analyzer agent fills in. Must contain:

   a. **Header block:** Analysis Date, Codebase Health rating (Good/Moderate/Concerning), Primary Language, Project Size (files/dirs).

   b. **Executive Summary table** (7 rows, 3 columns: Dimension, Finding, Confidence):
      - Architecture (from ARCHITECTURE.md)
      - Tech Stack (from STACK.md)
      - Code Quality (from CONVENTIONS.md)
      - Testing (from TESTING.md)
      - Integrations (from INTEGRATIONS.md)
      - Structure (from STRUCTURE.md)
      - Concerns (from CONCERNS.md)

   c. **Top Concerns section** — Top 3-5 from CONCERNS.md ranked by impact, each with severity tag (critical/moderate/minor).

   d. **7 detailed sections** (one per codebase document), each specifying:
      - `[Source: .planning/codebase/XXXX.md]` — which document to read
      - What to extract from that document (specific fields/sections)
      - Length constraint: 5-10 lines max per section
      - Format: bullets preferred, not prose paragraphs

   e. **Footer** — analysis date, update guidance.

3. **`<good_examples>`** section — a realistic filled-in example of a completed brownfield-analysis.md. Create a plausible example for a mid-size Next.js + Prisma project. This helps the analyzer agent understand expected compression level and format.

4. **`<guidelines>`** section — explain:
   - What belongs vs. what does NOT belong
   - Two-tier structure: executive summary for user presentation, detailed sections for reference
   - OBSERVED vs INFERRED distinction requirement
   - File paths must be included from source documents
   - The template is NOT the analysis — it's the structure the analyzer fills in

**Key design decisions (from 01-RESEARCH.md):**
- Each section maps 1:1 to one of the 7 codebase documents (prevents accidental omission)
- Each section specifies extraction instructions (not just a heading like "Architecture")
- Two-tier design prevents user fatigue on 200+ line documents
- Confidence tags (HIGH/MEDIUM) distinguish observed facts from inferred assessments
- Executive summary table enables quick scanning before purpose selection (fix/improve/refactor)

**Anti-patterns to avoid (from 01-RESEARCH.md Pitfall 1, 5):**
- DO NOT create vague section headings without extraction instructions
- DO NOT omit the good_examples section (agents need examples to calibrate output quality)
- DO NOT make all sections the same length (Concerns deserves more detail than Structure)
- DO NOT omit source document references (the agent needs to know where to look)
